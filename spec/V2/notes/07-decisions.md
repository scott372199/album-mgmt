# 07 · 决策记录 / Decision Records

| 项 / Item | 值 / Value |
| --- | --- |
| 状态 / Status | Approved |
| 用法 / Usage | 实现时遇到"为什么这样"先查这里；本文件只写结论与代价，不写过程 |
| 编号 / IDs | `ADR-nnn`，永久唯一，不复用、不改语义 |

每条包含四项：**决策**（做什么）、**理由**（一句）、**代价**（承认什么）、**影响**（改哪里）。

## 1. 架构 / Architecture

| # | 决策 / Decision | 理由 / Rationale | 代价 / Cost | 影响 / Affects |
| --- | --- | --- | --- | --- |
| **ADR-001** | 模块化单体（Spring Modulith），不拆微服务 | 2,000 资源、1–3 人的规模下，服务间网络开销与运维成本是纯负担 | 单点部署；模块边界只能靠编译期规则守 | `01` §6、`02` §10 |
| **ADR-002** | **层目录编号就是 apply 顺序**：`00-bootstrap → 01-storage → 02-data → 03-compute → 04-edge`，三站同构 | 只要保留一条反向依赖，层号就失去意义；把数据层放到计算层之前、边缘层放到计算层之后，反向边归零，顺序无需再额外声明 | 需要一次目录重排与销毁重建（见 ADR-041）；`02-data` 必须真实存在，不能把数据类资源塞在计算层 | `README` §3、`01` §8.1、`03` 表 `layer`、`08` E1 |
| **ADR-003** | **全部 16 个 scope 的 state 统一放 Azure Blob + lease**，S3 后端废弃 | state 是恢复能力的根，不能与要恢复的对象在同一朵云 | CI 需要 Azure 联邦凭据（与 AWS 并存）；S3 桶的 state 只作只读归档 | `01` §11.3、`08` E2 |
| **ADR-004** | 平台本体部署在 Azure（CONTROL 平面） | AWS 出故障时必须有指挥台能 `terraform plan`、能读凭据 | 团队要维护一点 Azure 技能；跨云出站调用延迟 | `01` §5.2、`08` 图 |
| **ADR-005** | 不用 Kafka，用 Modulith Event Publication Registry | 事件量级 < 1k/天，DB 表足够，且天然具备 outbox 语义 | 吞吐上限低；无跨进程消费 | `01` §6.2 |
| **ADR-006** | 不用 Athena，用嵌入式 DuckDB 直读 Blob 上的 Parquet | 数据量 < 5 GB，Athena 的元数据与权限配置成本高于收益 | 查询受单机内存限制；并发差 | `01` §9、`02` §4.2 |
| **ADR-007** | 不用图数据库，边存在 PostgreSQL 表里 | 节点 16 个、边 < 40 条，三跳 BFS 在内存里做 | 无法扩展到万级节点（当前不需要） | `03` 表 `stack_edge` |
| **ADR-008** | 平台不直连任何 state 桶，只消费 CI 产出的 `terraform show -json` 快照 | state 的存储格式不是稳定契约，JSON 输出是 | 依赖 CI 侧的 `iac-snapshot.yml` 先就位 | `01` §12 I3、`03` 表 `iac_snapshot` |
| **ADR-009** | 前端不跑力导向布局，坐标由后端给 | 同一份数据每次打开位置必须一致，否则用户无法建立空间记忆 | 布局算法要自己写；新增节点需重算 | `02` R-GRP-10、`03` 表 `stack_layout` |
| **ADR-010** | 图表全部手写 SVG，不引图表库 | 图谱、瀑布图、矩阵都是定制图形，图表库带来的是配置负担 | 开发量更大；交互细节要自己实现 | `05` §4 |

## 2. 多云模型 / Multi-cloud model

| # | 决策 | 理由 | 代价 | 影响 |
| --- | --- | --- | --- | --- |
| **ADR-011** | 一期即覆盖 AWS / GCP / Azure 三云，不做"二期补齐" | 三云的资源已经存在，晚接一天就多一天盲区；且统一模型一旦按两云定型，第三云会推翻它 | 首期工作量约多 35% | `01` §7、`02` §1 |
| **ADR-012** | 资源域用 LTREE 树（`scope_node`），不用扁平 `account/env/service` 三元组 | 三云层级不同（AWS 账号 / GCP 项目 / Azure 订阅 + RG），树能容纳差异且支持子树查询 | LTREE 标签需规范化（数字开头加前缀） | `03` 表 `scope_node` |
| **ADR-013** | `canonical_type` 存数据表 `type_mapping`，不用 Java 枚举 | 映射要能改、要能看覆盖率，改一次不应发版 | 多一次 join；需保证映射完整性 | `02` R-INV-07、`03` 表 `type_mapping` |
| **ADR-014** | 规定 6 个规范标签（`app/site/layer/env/owner/cost-center`），其余标签全量存 `tags_raw` | 分摊只需要少数维度；但未来维度不可预知，不能丢原始标签 | 需处理三云标签键大小写与命名限制 | `01` §7.3、`02` R-INV-08/09 |
| **ADR-015** | 区域统一到 metro，用于跨云比较 | `ap-southeast-1` 与 `asia-southeast1` 是同一个地方，region 名比较没有意义 | 需维护映射表 | `01` §7.5 |
| **ADR-016** | 能力矩阵显式声明三云差异，不假设等价 | 假设等价会导致采集器在缺能力时静默返回空 | 前端需处理"此云不支持"态 | `01` §7.6 |

## 3. 栈图谱 / Stack graph

| # | 决策 | 理由 | 代价 | 影响 |
| --- | --- | --- | --- | --- |
| **ADR-017** | 图谱节点 = `(site, layer)`，不抽象"服务"层 | `site.yaml` + 目录结构已经是精确的拓扑声明，再加一层抽象必然失真 | 跨层的业务概念（如"上传链路"）无法直接表达 | `01` §8.1 |
| **ADR-018** | 边按六级来源赋权（结构 / remote_state 1.0 → 标签 0.70），并强制携带 `evidence` | 用户必须能区分"代码写死的依赖"和"标签猜的关系" | 每条边都要有生成逻辑与证据文本 | `01` §8.2、`02` R-GRP-02 |
| **ADR-019** | 标签推断的边默认不画 | 推断关系噪声大，画出来会让图失去可读性 | 需要"展开推断关系"的交互 | `02` R-GRP-04、`05` §2.3 |
| **ADR-020** | 层 `kind` 与资源 `canonical_type` 不一致时只标记不阻断 | 现实里总会有人把队列顺手放进计算层；阻断会逼人绕开平台，标记才会暴露它 | 需维护"允许组"表 | `02` R-INV-14、`03` 视图 `v_layer_fit` |

## 4. 成本 / Cost

| # | 决策 | 理由 | 代价 | 影响 |
| --- | --- | --- | --- | --- |
| **ADR-021** | 先归一（FOCUS）再分摊，未归一的原始行只进 `raw_*` | 分摊算法改十次也不该动原始数据 | 多一层 ETL；FOCUS 字段多 | `02` R-FIN-01..04 |
| **ADR-022** | BILLED / AMORTIZED / ALLOCATED 三口径同时存在，不做"选一个" | 财务看 BILLED、决策看 ALLOCATED，砍掉任一个都会导致数字对不上 | 三套计算与三套校验 | `02` R-FIN-04、`05` §2.4 |
| **ADR-023** | 分摊四步固定顺序，不可跳步 | 跳步会让"为什么这个 stack 少了钱"无法回答 | 标签不全时覆盖率低，需暴露而非掩盖 | `02` R-FIN-07 |
| **ADR-024** | 未分配金额单独成行，禁止摊进任何 stack | 摊平是短期好看、长期失去信任的做法 | 页面上会一直有一条不好看的数字 | `02` R-FIN-06、`04` §6.1 |
| **ADR-025** | 每个金额必须带 `basis` + `precision` 四元组 | 没有精度标注的金额一定会被误用 | 所有端点、组件、导出都要改造 | `04` §1.2、`05` §2.4 |

## 5. 漂移与治理 / Drift and governance

| # | 决策 | 理由 | 代价 | 影响 |
| --- | --- | --- | --- | --- |
| **ADR-026** | 漂移双通道：日频属性对账 + 周频 `plan -refresh-only` | 前者快但只看属性；后者慢但能发现代码与 state 的关系问题 | 两套判定逻辑与两套证据格式 | `02` §3 |
| **ADR-027** | 漂移最小单位是 `(资源, 属性)`，不是资源 | 只有到属性才能判严重度，"这个资源有漂移"没有信息量 | 结论条数变多，需要聚合视图 | `02` R-DRF-01 |
| **ADR-028** | 漂移严重度只看两维：属性敏感性 × 可用性影响 | 引入概率或评分会让判定不可复现 | 边界情况需人工裁定 | `02` R-DRF-04 |
| **ADR-029** | 通道 B 失败记 `INCONCLUSIVE`，不得记为"0 条" | "未能判断"与"没有问题"混同是这类系统最常见的谎 | 前端需专门样式 | `02` R-DRF-09、`05` §2.6 |
| **ADR-030** | 平台不执行 apply，只 dispatch 一次 workflow，且需双人确认 | 写操作的唯一入口必须是 CI；平台持有写权限就会成为最大风险 | 单人团队场景需要两个账号 | `02` R-DEL-05/06、`04` §7.3 |
| **ADR-031** | 不给安全评分，不给等级 | 评分是伪精度，会让"72 分"取代真正的清单 | 需要按类与严重度组织页面 | `02` R-SEC-02 |
| **ADR-032** | 不存日志，只提供带时间范围与过滤的原生查询链接 | 日志存储是另一个产品，做不好还不如不做 | 用户需跳转一次 | `02` R-OBS-06 |
| **ADR-033** | 告警不合并到平台侧规则引擎，只做 30 分钟窗口聚合 | 双份告警规则必然不一致 | 平台无法"静默一条告警"，只能标记已读 | `02` R-OBS-04 |

## 6. 运维与容灾 / Operations and DR

| # | 决策 | 理由 | 代价 | 影响 |
| --- | --- | --- | --- | --- |
| **ADR-034** | 权威 DNS 在 Azure DNS，跨云入口用 DNS 层 failover | 60 秒级切换对当前 RTO 足够，且不把 Azure 变成数据面组件 | DNS 传播受 TTL 约束；需按域分层设 TTL | `01` §5.3 |
| **ADR-035** | 不引入 Front Door / Traffic Manager 做全局入口 | 秒级切换换来"全站可用性压在单一产品上"，不划算 | 切换慢几十秒 | `01` §5.3、`08` 图 |
| **ADR-036** | 容灾矩阵的 RTO/RPO 只认演练实测值，未演练显示"未验证" | 理论值在真故障时会造成误判，比"不知道"更危险 | 需要持续演练 | `02` R-PLT-13、`04` §11.1 |
| **ADR-037** | 平台不执行容灾切换，只提供矩阵与 runbook | 误判的自动切换造成的损失，通常大于多停几分钟 | 切换仍需人工 | `02` R-PLT-17 |
| **ADR-038** | 单租户、两角色（OWNER / VIEWER） | 内部工具，复杂 RBAC 只会增加配置错误 | 无法按项目分权 | `02` R-PLT-01/02 |
| **ADR-039** | 云凭据只存 Key Vault，用托管身份读取 | 环境变量与数据库都会在日志或转储中泄露 | 需保证 Key Vault 可用，否则降级 | `02` R-PLT-05/06 |
| **ADR-040** | `mgmt_enabled` 只作为受管状态位展示，平台不改它 | 改开关就是改基础设施，越过了 `ADR-030` 的边界 | 用户仍需手动改 tfvars | `02` R-INV-10、`README` §3 第 5 行 |
| **ADR-041** | 层序重排与 state 换云**用销毁重建，不做 state 迁移** | 目录名改了 state key 就变，而重建后的资源身份本来也会变；迁移只会把两套拓扑混在一份 state 里 | 一次计划内停机；DNS 与外部端点会变；必须先满足四条前提 | `08` E1/E2 |
| **ADR-042** | 三个站点层结构完全同构（五层），共享层单独叫 `s00-account` | 同构才能用一套 CI 矩阵、一套断言、一套图谱规则；差异只允许出现在 tfvars 里 | 某些站点会有空层（如 management 的 `02-data`），空层也要存在 | `00` §4、`README` §3.1 |

## 7. 容易被违反、需要复核的条目 / Most-likely-to-be-violated

实现评审时优先检查这七条，它们是这个设计里最容易被"顺手简化"掉的部分。

| # | 决策 | 违反后的症状 |
| --- | --- | --- |
| ADR-002 | 层号 = apply 顺序 | 有人为了"理顺"把 edge 提到 02，或把队列塞进 `03-compute` → 反向边重新出现，图谱与 apply 顺序同时失真 |
| ADR-008 | 平台不直连 state 桶 | 有人写了个直接读 `terraform.tfstate` 的解析器 → 半年后 Terraform 升版全线挂 |
| ADR-024 | 未分配不摊平 | 有人为了"图好看"把它按比例摊掉 → 成本数字再也对不上账单 |
| ADR-029 | `INCONCLUSIVE` 不能当 0 | 有人把失败吞掉返回空列表 → 漂移看板长期全绿，出事时无人相信 |
| ADR-030 | 平台不执行 apply | 有人为了"方便"给平台加了 apply 权限 → 平台变成最高权限单点 |
| ADR-036 | RTO 只认演练值 | 有人填了理论值且从不演练 → 真切换时 RTO 翻三倍 |
| ADR-025 | 金额四元组 | 有人图省事只返回数字 → 三口径混用，所有对比失效 |
